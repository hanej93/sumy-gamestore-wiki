# 주요 기술 결정

기술을 고를 때마다 **결정 / 근거 / 되돌리는 방법**을 기록했습니다(지금까지 40건). 그중 설명할 가치가 큰 것만 골랐습니다.

---

### 1. store는 WebFlux가 아니라 MVC + 가상 스레드
- **결정**: 게이트웨이와 알림은 WebFlux, 스토어는 Spring MVC에 JDK 21 가상 스레드를 씁니다.
- **근거**: JPA는 블로킹입니다. WebFlux에서 쓰면 이벤트 루프 스레드가 DB를 기다리며 막힙니다. 가상 스레드를 쓰면 코드는 순서대로 읽히는 블로킹 코드로 두면서 비슷한 동시 처리량을 얻습니다.
- **대안**: R2DBC로 전부 리액티브. JPA 생태계(지연 로딩, JDSL, 검증된 트랜잭션 모델)를 포기해야 해서 택하지 않았습니다.

### 2. 헥사고날 구조를 Gradle 모듈과 테스트로 강제
- **결정**: domain / application / adapter / bootstrap 모듈로 나누고, 의존 방향을 Konsist 테스트로 검사합니다.
- **근거**: 구조 규칙은 문서로만 두면 시간이 지나며 무너집니다. 빌드가 실패하게 만들면 사람과 AI 모두 지킬 수밖에 없습니다.

### 3. 조건부 쿼리는 Kotlin JDSL
- **결정**: 단순 조회는 Spring Data, 조건·조인·집계는 Kotlin JDSL로 씁니다.
- **근거**: 메서드 이름 쿼리는 조건이 늘면 읽을 수 없게 됩니다. QueryDSL은 코드 생성이 필요하고 Kotlin 지원이 약합니다. JDSL은 타입 안전하고 코드 생성이 없습니다.

### 4. 이중 결제는 "확정 시점 재확인 + PG 자동 취소"로
- **결정**: 회원·게임당 대기 주문을 하나로 제한하지 않습니다. 결제 확정 트랜잭션에서 보유 여부를 다시 확인하고, 이미 보유했다면 PG 결제를 전액 취소합니다.
- **근거**: 대기 주문을 하나로 제한하면 결제창을 닫고 다시 시도하는 정상 사용자를 막게 됩니다. 확정 시점 재확인과 보상 취소는 PG 연동 가이드가 권하는 "서버 검증 실패 시 결제 취소"와 같은 방식이고, API 응답도 바뀌지 않습니다.
- 자세한 과정: [트러블슈팅 2](../troubleshooting/02-double-payment.md)

### 5. 외부 호출은 트랜잭션 밖에서
- **결정**: PG 호출, 보상 취소는 모두 DB 트랜잭션 밖에서 합니다. 확정은 "읽기 트랜잭션 → PG 조회 → 쓰기 트랜잭션"으로 나눴습니다.
- **근거**: 트랜잭션 안에서 외부를 부르면 PG가 느릴 때 DB 커넥션과 행 잠금을 붙잡습니다. 또 "실패 기록"이 뒤이은 예외와 함께 롤백돼 사라집니다.

### 6. 웹훅 서명은 PortOne 공식 SDK로 검증
- **결정**: 웹훅 본문은 "이 결제를 다시 보라"는 신호로만 쓰고, 실제 상태는 PG에 다시 조회해 확정합니다. 서명 검증은 직접 구현하지 않고 공식 SDK(Standard Webhooks 규격)를 씁니다.
- **근거**: 본문을 믿으면 위조된 웹훅으로 주문을 확정시킬 수 있습니다. 서명 검증처럼 틀리기 쉬운 보안 코드는 직접 만들지 않습니다.

### 7. 오류는 ProblemDetail + 스펙 검사
- **결정**: 모든 오류를 RFC 9457 ProblemDetail로 내고, OpenAPI 스펙이 실제 응답과 같은지 스크립트로 검사합니다.
- **근거**: 프론트엔드가 스펙에서 타입을 생성합니다. 스펙이 응답과 다르면 프론트엔드에서 런타임 버그가 됩니다. 실제로 nullable 표시가 빠져 화면에 1970년 날짜가 찍힌 적이 있어 검사를 넣었습니다.

### 8. 운영 기본값은 안전한 쪽으로
- **결정**: 운영 프로파일에서 PG 키나 웹훅 서명 키가 없으면 앱이 기동하지 않습니다. 시드 관리자 계정은 로컬 프로파일에서만 만듭니다.
- **근거**: "기본값은 로컬에서 그냥 돌아가게" 만들어 두면 운영에서 가짜 결제나 공개된 관리자 계정이 조용히 켜질 수 있습니다. 설정이 빠졌을 때는 늦게 깨지기보다 빨리 실패하는 편이 낫습니다.

### 9. 비밀값은 코드 밖으로
- **결정**: 모든 비밀값은 환경 변수로 받고, 저장소에는 키 이름만 둡니다. Helm은 서비스별 시크릿을 참조하고, 시크릿 자체는 만들지 않습니다.
- **근거**: 레거시 프로젝트에는 메일 비밀번호와 외부 API 키가 평문으로 들어 있었습니다. 재작성하면서 가장 먼저 바로잡은 부분입니다.

### 10. 표준 라이브러리가 있으면 직접 만들지 않는다
- **결정**: 레이트리밋은 게이트웨이 내장 리미터, 분산 스케줄은 ShedLock, 웹훅 서명은 PG 공식 SDK를 씁니다. 직접 만든 추적 ID 필터는 다음 단계에서 Micrometer Tracing의 자동 전파로 바꿉니다.
- **근거**: 직접 만든 공통 코드는 유지보수 비용이 계속 듭니다. 설계를 다시 검토하면서 직접 구현하려던 것들(2단 캐시, 범용 사가 프레임워크, 엑셀 매핑 프레임워크 등)을 표준 도구로 바꾸거나 계획에서 뺐습니다.
