# 프로젝트 소개

예전에 만든 게임 쇼핑몰을 Kotlin·Spring Boot 4 백엔드와 Next.js 프론트엔드로 처음부터 다시 만드는 개인 프로젝트입니다. 기능 요구사항은 레거시에서 가져오고, 구현은 하나도 베끼지 않았습니다.

## 배경: 레거시는 어떤 상태였나

레거시는 Java 8, Spring Boot 2.7, JSP, MyBatis로 만든 단일 애플리케이션이었습니다. 테이블 10개, 업무 영역 8개(회원·카탈로그·주문결제·위시리스트·리뷰신고·문의·뉴스·관리자) 규모입니다.

재작성 전에 코드를 직접 읽어 분석했습니다. 결과는 이렇습니다.

| 항목 | 확인한 수치 |
|---|---|
| 소스에 평문으로 들어 있던 자격 증명 | 18건 (그중 즉시 폐기 대상 8건) |
| 스키마 문제 | 43건 |
| Bean Validation 사용 | 0건 |
| 전역 예외 처리(`@ControllerAdvice`) | 0건 |
| 예외를 `printStackTrace()`로 삼키고 계속 진행 | 18곳 |
| `System.out.println` 로그 | 70건 |
| 같은 페이징 기본값 코드를 복사한 컨트롤러 | 9개 |
| 파일 업로드 로직 중복 | 4벌 |

숫자보다 심각한 것은 구조적인 결함이었습니다. 결제 승인 단계가 없어 **결제 없이 구매를 확정하는 경로**가 있었고, 인가 설정이 주석 처리돼 있어 **인증 없이 다른 계정의 비밀번호를 바꾸는 경로**가 있었습니다. 결제 금액은 화면 DOM에서 읽어 그대로 PG로 넘겼습니다. 그래서 주문·결제 영역은 "이관"이 아니라 "폐기 후 재설계"로 판단했습니다.

자세한 내용은 [레거시 분석 요약](legacy-analysis.md)에 있습니다.

## 목표

1. **레거시의 기능을 안전하게 다시 만든다.** 결제·인가·검증처럼 돈과 계정이 걸린 부분은 테스트로 증명합니다.
2. **구조 규칙을 빌드가 지키게 한다.** 의존 방향을 Gradle 모듈과 아키텍처 테스트로 막습니다.
3. **실제로 띄워서 확인한다.** 컴파일·단위 테스트만으로 끝내지 않고, 커밋 전에 전체 서비스를 띄워 API를 호출합니다.
4. **공통 Spring 스타터 플랫폼의 기준 구현이 된다.** 플랫폼에 넣을 기술을 이 프로젝트에 먼저 적용해 보고, 공통 코드를 스타터로 추출합니다(계획, 백엔드 D20).

## 범위

| 영역 | 구현한 기능 |
|---|---|
| 회원·인증 | 가입, 폼 로그인, 카카오·네이버 소셜 로그인, Redis 세션, 생년월일 등록, 정지 시 세션 회수 |
| 카탈로그 | 검색·카테고리·가격 필터·정렬·페이징, 관리자 게임 등록·수정·판매 상태 전이, presigned URL 이미지 업로드 |
| 주문·결제 | 서버 금액 계산, 가격 스냅샷, PortOne 결제 검증(키가 없으면 가짜 어댑터), 미결제 주문 취소, 이중 결제 자동 취소, 결제 웹훅 서명 검증, 미확정 주문 대사 |
| 위시리스트·라이브러리 | 담기·빼기, 구매 시 위시리스트 자동 정리, 보유 게임 목록 |
| 리뷰·신고 | 보유자만 리뷰 작성, 좋아요, 신고, 관리자 신고 처리, 제재 이력 |
| 문의·뉴스 | 문의 등록·답변·종료, 공지·뉴스 |
| 관리자 | 회원·게임·신고·문의 관리 API와 화면 |
| 알림 | 주문 이벤트를 Kafka로 받아 메일 발송(별도 서비스, 자체 DB) |
| 프론트엔드 | 화면 21개, OpenAPI 타입 생성, 장바구니, 관리자 화면 |

!!! note "아직 하지 않은 것"
    서비스 분리, 이벤트 아웃박스, CD 키 발급, 환불, 검색 엔진, 국제화, 실제 PG 키 연동은 **계획**입니다. [로드맵](roadmap.md)에 있습니다.

## 기간과 규모

아래 수치는 모두 저장소에서 직접 셌습니다(2026-10-20 기준). 줄 수는 빈 줄과 주석을 포함합니다.

| 항목 | 백엔드 | 프론트엔드 |
|---|---|---|
| 첫 커밋 | 2026-09-24 | 2026-09-24 |
| 커밋 수 | 73 | 26 |
| 언어 | Kotlin | TypeScript |
| 소스 파일 | Kotlin 파일 210개 (테스트 포함) | TypeScript 파일 90개 (생성 타입 제외) |
| 운영 코드 | 12,402줄 | 6,579줄 |
| 테스트 코드 | 7,022줄 | E2E 645줄 |
| 테스트 수 | 416개 (최근 실행 보고서 기준) | E2E 시나리오 20개 |
| 기타 | Flyway 마이그레이션 13개, API 연산 63개 | 화면(라우트) 21개 |
| 완료한 작업 카드 | 19장 | 11장 (검토 중 1장, 보류 1장) |
| 결정 기록 | 40건 (D01~D40) | 22건 (D01~D22) |

백엔드 운영 코드 12,402줄 가운데 11,827줄이 스토어 서비스입니다. 게이트웨이는 193줄, 알림 서비스는 224줄, 공통 모듈은 158줄입니다. 게이트웨이와 알림은 역할이 좁아서 작게 유지했습니다.

## 레거시 대비 바뀐 것

| 항목 | 레거시 | 재작성 |
|---|---|---|
| 언어·런타임 | Java 8 | Kotlin 2.2, JDK 21 (가상 스레드) |
| 프레임워크 | Spring Boot 2.7 | Spring Boot 4.0, Spring Cloud Gateway |
| 화면 | JSP 서버 렌더링 | Next.js 16 별도 저장소, API로만 통신 |
| 배포 단위 | 애플리케이션 1개 | 게이트웨이·스토어·알림 3개 |
| 구조 | 컨트롤러가 도메인 규칙과 외부 API 호출까지 수행 | 헥사고날. 도메인 모듈은 프레임워크 의존 0, 규칙은 테스트로 강제 |
| 데이터 접근 | MyBatis, 문자열 치환(`${}`) 혼재 | JPA + Kotlin JDSL. 문자열 SQL을 쓰지 않음 |
| 스키마 관리 | SQL 덤프 하나 | Flyway 마이그레이션. `ddl-auto`는 `validate` 고정 |
| 결제 | 승인 단계 없음, 금액을 화면에서 받음 | 서버가 금액 계산, PG 실결제액 대조, 웹훅 서명 검증, 동시 확정·취소 직렬화 |
| 인가 | 대부분 공개, CSRF 꺼짐 | 기본이 닫힘, 공개 경로만 나열 |
| 입력 검증 | 0건 | 요청 객체 검증 + 도메인 불변식 + DB 제약 |
| 오류 응답 | 엔드포인트마다 다른 타입 | RFC 9457 ProblemDetail로 통일 |
| 로그 | `System.out` | 구조화 JSON 로그 + 추적 ID |
| 비밀값 | 소스·설정에 평문 | 환경 변수로만. 저장소에는 키 이름만 |
| 파일 | 서버 로컬 디스크(윈도우 경로 하드코딩) | S3 호환 스토리지, 브라우저 직접 업로드 |
| 서비스 간 연동 | 없음 | Kafka 도메인 이벤트 |
| 테스트 | (분석 범위 밖) | 백엔드 416개(Testcontainers), 실제 기동 스모크, 프론트 E2E |
| 배포 | 저장소에 배포 설정 없음 | Docker 이미지, Helm 차트, GitHub Actions |
