# 레거시 분석 요약

재작성을 시작하기 전에 레거시 코드·SQL 매퍼·화면·스키마를 직접 읽고, 확인한 것만 근거와 함께 기록했습니다. 이 분석이 "무엇을 가져오고 무엇을 버릴지"의 기준이 됐습니다.

## 분석 방법

- 업무 영역 8개별로 컨트롤러·서비스·매퍼·화면·테이블을 짝지어 기능 목록을 만들었습니다. 기능 목록은 컨트롤러 메서드와 매퍼 SQL에서 뽑았습니다.
- 발견한 문제는 모두 파일과 줄 번호를 붙여 적었습니다. 추측은 넣지 않았고, 열어 보지 못한 자료(바이너리 화면 설계서 등)는 "미확인"으로 남겼습니다.
- 조사는 AI 에이전트 3개로 나눠 병렬로 했고, 핵심 주장(결제 승인 부재, 인가 주석 처리, 문자열 SQL 치환, 고정 비밀번호)은 파일을 직접 열어 다시 확인했습니다.
- 산출물은 네 개입니다. 색인과 취약점 요약, 도메인 분석, 스키마 분석(ERD, 문제 43건), 자격 증명 감사(18건)입니다.

## 문제 범주

| 범주 | 주요 문제 | 규모 |
|---|---|---|
| 보안: 인증·인가 | `/user/**` 인가가 주석 처리되고 나머지 전부 공개, CSRF 꺼짐. 요청 본문의 회원 ID를 그대로 믿음. 리뷰·위시리스트 수정·삭제에 소유자 확인 없음. 정지 회원도 로그인 가능 | 11항목 |
| 보안: 결제 | 승인 단계 없음. 금액을 화면 DOM에서 읽어 서버가 재계산 없이 PG로 전달. 합계가 0 이하이면 PG를 건너뛰고 구매 확정 | 7항목 |
| 보안: 비밀값 | 메일 계정 비밀번호, 소셜 로그인·결제 API 키, DB 계정, 관리자 계정이 소스·설정·문서에 평문 | 18건 (즉시 폐기 8건) |
| 보안: SQL | MyBatis `${}` 문자열 치환으로 조건을 SQL에 직접 삽입. PG 요청 파라미터도 문자열 연결 | 3항목 |
| 데이터 모델 | 카테고리 4칸·소개 이미지 5칸·문의 이미지 3칸 고정 컬럼. 별점을 문자열 enum으로 저장하고 평균을 계산. 외래 키 13개 모두 삭제 동작 없음. 판매 수를 동시성 보호 없이 갱신 | 스키마 문제 43건 |
| 구조 | 컨트롤러가 외부 API를 직접 호출하고 도메인 규칙까지 수행. 트랜잭션이 없는 서비스 11개. 응답 타입이 엔드포인트마다 다름. 조회 API를 POST로 구현 | 기술 부채 13개 범주 |
| 버그 | 컬럼 목록에 콤마가 빠진 INSERT, 실제 컬럼과 이름이 다른 INSERT, MySQL 문법이 아닌 UPDATE. 단건 결제 시 산 게임과 무관하게 위시리스트 첫 항목 삭제. 이미지 없이 수정하면 기존 이미지 경로를 null로 덮어씀 | 14항목 |
| 운영 | 검증 0건, 전역 예외 처리 0건, `printStackTrace()` 18곳, `System.out` 70건, 업로드 경로가 윈도우 절대 경로 | — |

스키마 문제 43건의 구성은 반복 컬럼·정규화 위반 6, 타입·도메인 표현 8, 파일 저장 5, 제약·정합성 9, 모델 누락 9, 이름·일관성 4, 인덱스·기타 2입니다.

## 대표 사례

### 1. 결제 없이 구매가 확정된다

카카오페이는 "준비 → 사용자 승인 → 승인 확인" 3단계입니다. 그런데 레거시 코드에는 승인 확인 호출이 한 번도 나오지 않았습니다(관련 문자열 검색 0건). 결제 성공 후 돌아오는 주소가 검증 없이 구매를 확정했으므로, 그 주소만 호출하면 결제 없이 게임을 얻을 수 있었습니다. 게다가 결제 금액은 화면 DOM의 텍스트였습니다.

**재작성**: 주문을 독립된 애그리거트로 새로 설계했습니다. 총액은 서버가 현재 카탈로그 가격으로 계산하고, 주문 줄에 가격을 스냅샷으로 남깁니다. 확정할 때 PG에서 실제 결제 금액을 조회해 주문 금액과 비교합니다. 이후 이중 결제 자동 취소(T25), 웹훅 서명 검증과 미확정 주문 대사(T26)까지 더했습니다.

### 2. 인증 없이 다른 계정을 가져갈 수 있다

인가 설정의 `/user/**` 보호가 주석 처리돼 있었고 CSRF도 꺼져 있었습니다. 비밀번호 재설정 엔드포인트는 요청 본문의 회원 ID만 보고 비밀번호를 바꾼 뒤 그 계정으로 로그인 상태까지 만들어 줬습니다.

**재작성**: 인가 기본값을 "닫힘"으로 두고 공개 경로만 나열했습니다. 회원 식별자는 요청 본문이 아니라 세션의 인증 주체에서만 꺼냅니다. 남의 주문에 접근하면 존재 여부가 드러나지 않도록 403이 아니라 404를 줍니다.

### 3. 소셜 로그인 회원 전원이 같은 비밀번호를 가진다

카카오로 가입한 회원에게 소스에 박힌 고정 비밀번호를 부여했습니다. 그 값을 알면 해당 이메일로 폼 로그인을 할 수 있었습니다.

**재작성**: 소셜 가입 회원은 비밀번호가 없는 상태로 만듭니다. 이 성질을 도메인 테스트로 고정했습니다(백엔드 T02). 카카오는 인증된 이메일일 때만 기존 계정과 연결합니다(백엔드 D40).

### 4. 비밀값이 저장소에 평문으로 있다

자격 증명 18건이 소스·설정·문서에 있었고, 저장소가 공개 상태였기 때문에 모두 유출된 것으로 봤습니다. 감사 문서에도 값은 적지 않고 위치만 적었습니다.

**재작성**: 모든 비밀값을 환경 변수로 받고 저장소에는 키 이름만 둡니다. 운영 프로파일에서 필수 키가 없으면 기동을 거부합니다. 레거시 저장소는 비공개로 바꿨고, 남은 키 폐기·재발급은 사람이 확인할 목록에 올렸습니다.

### 5. 고정 칸 컬럼과 문자열 별점

게임 카테고리는 `game_category_id1~4` 네 칸이라 필터 SQL마다 `OR` 네 개가 반복됐고, 소개 이미지는 다섯 칸으로 제한됐습니다. 별점은 문자열 `enum('1'..'5')`인데 SQL에서 평균을 냈습니다.

**재작성**: 카테고리는 조인 테이블, 이미지는 순서를 값으로 가진 별도 테이블로 바꿔 개수 제한을 없앴습니다. 별점은 1~5 범위를 지키는 값 클래스와 정수 컬럼, DB CHECK 제약으로 바꿨습니다. 신고·경고 카운터는 "왜, 언제까지"를 답할 수 있는 제재 이력 테이블로 바꿨습니다.

## 영역별 이관 판단

| 영역 | 판단 | 이유 |
|---|---|---|
| 회원·인증 | 이관 | 필수 기반입니다. 단 인증 구현은 전부 버리고 새로 만듭니다 |
| 게임 카탈로그 | 이관 | 검색·필터·정렬 SQL이 곧 요구사항 명세였습니다 |
| 주문·결제 | **폐기** | 그대로 옮기면 결제 없이 구매가 성립합니다. 요구사항만 뽑아 재설계했습니다 |
| 위시리스트·라이브러리 | 이관 | 로직이 단순합니다. 장바구니 겸용은 분리했습니다 |
| 리뷰·신고 | 이관 | 별점이 카탈로그 정렬에 쓰이고, 신고 → 경고 → 정지 흐름이 있습니다 |
| 문의 | 이관 | 등록 → 읽음 → 답변까지 동작하는 단순한 기능입니다 |
| 뉴스 | 이관 | 게시판 수준이고 메인 화면이 의존합니다 |
| 관리자 | 이관 | 운영에 필요합니다. 회원 삭제만 보류했습니다 |

!!! note "\"이관\"의 뜻"
    이관은 기능 요구사항을 가져온다는 뜻이고, 구현을 베낀다는 뜻이 아닙니다. 레거시 코드는 화면 흐름과 업무 규칙을 읽는 용도로만 참고했습니다.

## 문제와 대응 정리

| 레거시 문제 | 재작성의 대응 |
|---|---|
| 결제 승인 부재 | PG가 알려 준 실결제액과 주문액 대조, 웹훅은 서명 검증 후 "다시 조회하라"는 신호로만 사용 |
| 금액을 클라이언트에서 받음 | 판매가를 서버가 계산해 내려 줌. 프론트도 금액을 계산하지 않음 |
| 인가 공백 | 기본 닫힘, 공개 경로만 나열, 관리자 엔드포인트 권한을 전수 테스트 |
| 문자열 SQL | Kotlin JDSL. 값이 없는 조건은 만들지 않음 |
| 검증 0건 | 요청 객체 검증, 도메인 불변식, DB 제약의 세 겹 |
| 전역 예외 처리 0건 | 한 곳에서 RFC 9457 ProblemDetail로 통일 |
| `printStackTrace`·`System.out` | 구조화 JSON 로그와 추적 ID |
| 업로드 로직 4중복, 로컬 디스크 저장 | 저장소 포트 하나 뒤에 S3 어댑터 하나, 브라우저 직접 업로드 |
| 페이징 코드 9벌 복사 | 요청 객체 기본값과 공통 페이지 응답 |
| 트랜잭션 누락 | 유스케이스 단위 트랜잭션, 외부 호출은 트랜잭션 밖 |
