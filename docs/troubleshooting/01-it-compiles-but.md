# 1. 빌드도 테스트도 통과했는데, 실제로 띄우니 아무것도 안 됐다

## 상황
서비스 세 개(게이트웨이·스토어·알림)를 처음으로 Docker Compose로 한꺼번에 띄웠습니다. 그 전까지 빌드, 단위 테스트, CI의 이미지 빌드는 모두 초록이었습니다. 그런데 실제로 띄워 보니 문제가 여덟 개 나왔고, 하나같이 **컴파일과 테스트를 통과하는 종류**였습니다. 대표적인 네 가지를 정리합니다.

## ① 컨테이너가 시작하자마자 죽었다
- **증상**: `ClassNotFoundException`. 이미지 빌드는 성공했습니다.
- **원인**: Dockerfile이 Boot 3 방식대로 `JarLauncher`로 실행하고 있었습니다. Boot 4의 레이어 추출 결과는 그 구조가 아니라 일반 jar와 `lib/` 디렉터리였습니다.
- **해결**: `java -jar`로 실행하도록 바꾸고, 레이어 순서를 변경 빈도 순으로 맞춰 캐시가 살게 했습니다.
- **교훈**: CI의 "이미지 빌드 성공"은 컨테이너가 뜬다는 뜻이 아닙니다.

## ② 구매 확인 메일이 한 통도 나가지 않았다
- **증상**: 결제는 정상인데 알림 서비스 로그에 역직렬화 예외가 쌓였습니다.
- **원인**: 애플리케이션 JSON 처리는 Jackson 3인데, spring-kafka의 직렬화기는 아직 Jackson 2였습니다. 알림 서비스에는 Jackson 2용 Kotlin 모듈과 Java 시간 모듈이 없었습니다. 스토어 쪽은 다른 라이브러리가 우연히 시간 모듈을 끌어와서 발행만 멀쩡했습니다.
- **추가로 발견한 것**: 발행 쪽이 시각을 `1790819340.105566714` 같은 **소수 epoch 초**로 쓰고 있었습니다. 부동소수라 나노초가 유실되고, API의 "모든 시각은 ISO-8601" 약속과도 어긋났습니다.
- **해결**: 와이어 포맷(ObjectMapper 설정)을 공용 이벤트 모듈 한 곳에 두고 발행·구독 양쪽이 같은 것을 쓰게 했습니다. 시각은 ISO-8601 문자열로 고정했습니다. 읽을 수 없는 메시지 하나가 같은 오프셋에서 계속 재시도되며 뒤 메시지를 막지 않도록 `ErrorHandlingDeserializer`로 감쌌습니다.

## ③ 메시지가 파티션에 쌓였는데 아무도 처리하지 않았다
- **증상**: 일부 이벤트만 처리되고 나머지는 사라진 것처럼 보였습니다.
- **원인**: 알림 서비스가 먼저 뜨면 브로커가 토픽을 **기본값 1 파티션**으로 자동 생성합니다. 뒤늦게 스토어가 3으로 늘려도, 이미 붙어 있던 컨슈머는 메타데이터를 다시 읽을 때까지(기본 5분) 새 파티션을 받지 못했습니다. 실측해 보니 컨슈머는 0번 파티션만 잡고 있었고, 메시지는 1번에 쌓여 있었습니다.
- **해결**: 발행 쪽과 구독 쪽이 **같은 파티션 수로 토픽을 선언**하게 하고, 브로커의 토픽 자동 생성을 껐습니다. 알림 서비스를 가장 불리한 순서(먼저)로 띄워도 세 파티션을 모두 받는 것을 확인했습니다.

## ④ 메일 문구를 찾지 못해 발송이 매번 실패했다
- **원인**: 메시지 파일이 `i18n/` 아래에 있는데 basename을 지정하지 않았습니다. Boot는 루트의 `messages.properties`만 찾고, 없으면 MessageSource 자동설정이 통째로 빠집니다. 기동은 정상이고, 실제로 메일을 보낼 때만 예외가 났습니다.
- **해결**: basename을 지정하고, 이벤트 수신부터 메일 발송까지를 통합 테스트로 재현해 고정했습니다.

## 재발 방지
- 커밋 전 검증 스크립트가 **전체를 실제로 띄워** API를 호출하게 했습니다(스모크 130여 항목). 이 검증이 실패하면 커밋하지 않습니다.
- Testcontainers로 실제 Kafka·MySQL에 붙는 통합 테스트를 추가했습니다. 결제 후 메일이 도착하는 데까지 약 0.4초 걸리는 것을 확인했습니다.
- Boot 4에서 새로 만난 함정은 팀 문서(`Boot 4가 Boot 3와 다른 점`)에 계속 쌓습니다.

## 배운 점
Spring Boot 4는 자동설정이 모듈로 나뉘어 있어서, 필요한 빈이 없어도 컴파일은 통과합니다. **"컴파일 성공은 아무것도 보장하지 않는다"**를 원칙으로 삼고, 새 기술을 붙이면 반드시 실제로 띄워 보게 됐습니다.
