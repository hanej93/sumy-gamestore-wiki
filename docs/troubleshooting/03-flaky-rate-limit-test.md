# 3. 가끔만 실패하는 레이트리밋 테스트

## 상황
게이트웨이 레이트리밋 키를 "로그인 세션, 없으면 클라이언트 IP"로 바꾸고 통합 테스트를 넣었습니다. 테스트는 한도를 1(초당 1개, 버스트 1)로 낮추고 다음을 확인했습니다.

```
첫 번째 요청        → 200
같은 IP 두 번째 요청 → 429
다른 IP 요청         → 200
```

로컬에서는 매번 통과했는데, CI에서 한 번 "두 번째 요청이 200"으로 실패했습니다. 재실행하니 통과했습니다.

## 넘기지 않은 이유
재실행으로 통과했으니 넘어갈 수도 있었습니다. 하지만 가끔 실패하는 테스트는 결국 아무도 믿지 않게 되고, 진짜 실패도 "또 그거겠지" 하고 지나치게 만듭니다. 원인을 찾기로 했습니다.

## 원인
Spring Cloud Gateway의 Redis 레이트리미터는 토큰 버킷을 Lua 스크립트로 계산합니다. 이 스크립트가 쓰는 현재 시각이 Redis `TIME`의 **초 단위 정수**입니다.

예를 들면 이렇습니다.

```
요청 1: 12:00:00.998 → 시각 0초, 토큰 1 → 0   → 200
요청 2: 12:00:01.003 → 시각 1초, 1초 경과 → 토큰 1 다시 채움 → 200 (기대는 429)
```

두 요청 사이 간격이 5ms뿐이어도, 그 사이에 **초 경계**가 끼면 1초가 지난 것으로 계산돼 버킷이 다시 찹니다. 테스트가 느린 CI에서 실행되면서 이 경계에 걸릴 확률이 올라간 것이었습니다.

## 해결
요청 한 번이 쓰는 토큰 수(`requestedTokens`)를 설정으로 열었습니다. 운영 값은 그대로 1입니다. 테스트에서는 버킷 60, 초당 충전 1, **요청당 60**으로 둡니다. 이렇게 하면 요청 한 번이 버킷을 다 쓰고, 다시 차려면 60초가 걸립니다. 초 경계가 끼어도 1만큼만 차므로 두 번째 요청은 반드시 429가 됩니다.

고친 뒤 테스트를 연속으로 여러 번 돌려 흔들리지 않는 것을 확인했습니다. 원인과 해결은 테스트 코드 주석에도 남겼습니다.

## 배운 점
- **가끔 실패하는 테스트에는 반드시 이유가 있습니다.** 재실행 버튼은 원인을 숨길 뿐입니다.
- 시간에 의존하는 테스트는 "충분히 빠르면 통과"에 기대지 말고, 시간이 흘러도 결과가 바뀌지 않게 조건을 설계해야 합니다.
- 라이브러리 동작을 추측하지 않고 실제 구현(Lua 스크립트)을 읽어 확인한 것이 원인을 찾는 지름길이었습니다.
