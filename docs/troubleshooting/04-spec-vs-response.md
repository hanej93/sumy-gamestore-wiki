# 4. 화면에 1970년 날짜가 찍혔다: API 스펙과 실제 응답의 차이

## 상황
프론트엔드는 백엔드의 OpenAPI 스펙에서 TypeScript 타입을 생성해 씁니다. 그런데 결제하지 않은 주문의 결제 시각 칸에 **1970년 1월 1일**이 찍혔습니다.

## 원인
- 백엔드 응답의 `paidAt`은 결제 전에는 `null`입니다. Kotlin에서도 `Instant?`로 선언돼 있었습니다.
- 그런데 스펙에는 `paidAt`이 단지 "필수가 아님"으로만 나와 있었고, **null이 올 수 있다는 표시가 없었습니다.**
- 그래서 생성된 타입은 `paidAt?: string`이 됐습니다. 프론트엔드는 "없을 수도 있다"만 대비했고, `null`이 오자 `new Date(null)`이 1970년이 됐습니다.

같은 문제가 응답 필드 35곳에 있었습니다. 반대로 실제로는 항상 값이 있는 `id`가 스펙에서는 선택 필드로 나온 곳도 7곳 있었습니다. 오류 응답 형식도 스펙에는 자유형 맵으로만 적혀 있어서, 프론트엔드가 검증 오류 타입을 손으로 따로 써서 유지하고 있었습니다.

## 더 들어간 원인
springdoc에는 Kotlin nullable을 스펙에 반영하는 기능이 **이미 들어 있었습니다.** 그런데 이전에 다른 문제를 풀려고 직접 등록해 둔 스키마 처리기 빈이 그 기능을 가리고 있었습니다.

## 해결
1. 직접 등록한 빈을 지우고 springdoc 내장 기능을 쓰게 했습니다. 스펙 전후를 비교해 필수 필드가 줄어들지 않은 것을 확인했습니다.
2. 실제로 항상 값이 있는 응답 `id`는 non-null 타입으로 바꿨습니다.
3. 오류 응답 스키마를 **실제 응답에 쓰는 Kotlin 타입에서 생성**하게 했습니다. 스펙과 응답이 같은 타입에서 나오므로 둘이 따로 놀 수 없습니다.
4. 스펙 품질 검사 스크립트에 "선택 필드는 nullable 표시", "오류 응답은 정해진 형식"을 추가했습니다. 고치기 전 스펙으로 돌려 35건과 2건을 실제로 잡아내는 것을 확인한 뒤 넣었습니다.

결과적으로 프론트엔드는 손으로 쓴 오류 타입과 null 우회 코드를 지우고 생성 타입만 쓰게 됐습니다.

## 배운 점
- **스펙은 계약입니다.** 응답과 스펙이 어긋나면 컴파일러도 테스트도 잡지 못하고 화면에서 터집니다.
- 스펙을 손으로 고치지 않고 **같은 타입에서 생성**하게 만들어야 둘이 함께 바뀝니다.
- 프레임워크에 이미 있는 기능을 직접 만든 코드가 가리고 있지 않은지 먼저 확인하는 습관이 생겼습니다.
